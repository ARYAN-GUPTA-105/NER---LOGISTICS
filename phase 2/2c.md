# PHASE 2C — LIVE GPS & ROUTE TRACKING

## Objective

Introduce live location and map-based trip tracking for the Driver.

## Prerequisite

Phase 2A and Phase 2B must be complete.

---

# 1. LOCATION

The Driver experience should support:

* Current position
* Destination
* Route
* Distance remaining
* ETA
* Route progress

Use the browser/device geolocation capabilities appropriate for the selected platform.

Do not collect location when it is not necessary.

---

# 2. GPS STATE

Support states:

* GPS unavailable
* Permission required
* Acquiring location
* Active
* Temporarily unavailable
* Network unavailable

The UI must clearly communicate the current condition.

---

# 3. MAP

Display:

* Driver position
* Destination
* Current route
* Relevant route segments

The map should be designed for operational readability.

Do not overcrowd it with every possible future layer.

---

# 4. TRACKING ARCHITECTURE

Keep these concerns separate:

Location provider
→ Location state/service
→ Application state
→ Map presentation

Do not place tracking logic directly inside the map component.

The architecture should later support:

* Backend location updates
* Fleet monitoring
* Historical tracking
* Route recalculation

---

# 5. LOCATION UPDATES

Define a sensible update strategy.

Avoid:

* Excessive requests
* Battery-heavy behavior
* Unnecessary backend writes

The exact production strategy may be refined later.

---

# 6. ETA

The current architecture should allow ETA to be updated based on:

* Current position
* Remaining route
* Route conditions

Do not present fabricated precision as real data.

Clearly distinguish development/mock values from calculated values.

---

# 7. CONNECTIVITY

Show whether:

* GPS is available
* Network is available
* Data is synchronized

Offline behavior will be expanded in Phase 2F.

---

# 8. PERMISSIONS

Handle location permission denial gracefully.

Explain why location is required when needed.

Do not trap the user in a broken state.

---

# 9. RESPONSIVE DESIGN

The map and route controls must work on:

* 430px
* 390px
* 375px
* Tablet
* Desktop

Controls must remain touch-friendly.

---

# 10. SCOPE RESTRICTIONS

Do NOT implement:

* AI route prediction
* Complex route optimization
* Fleet management dashboard
* Authority GIS system
* Advanced disruption intelligence

Those belong to later phases.

---

# 11. ACCEPTANCE CRITERIA

* Driver location can be obtained where permission is available.
* GPS states are communicated.
* Driver appears on map.
* Destination appears.
* Route is visible.
* Trip progress is represented.
* Connectivity state is visible.
* Mobile experience is usable.
* No unnecessary location polling.
* No console errors.

# END PHASE 2C
