# PHASE 2E — ALERTS, INCIDENT REPORTING & DRIVER SAFETY

## Objective

Give the Driver tools to receive critical alerts and report real-world road incidents.

## Prerequisite

Phase 2D must be complete.

---

# 1. ALERT CENTER

Create a Driver alert experience.

Alerts may include:

* Road blocked
* Flood
* Landslide
* Route change
* High-risk route
* Severe delay
* Emergency warning

Each alert should support:

* Severity
* Title
* Message
* Timestamp
* Relevant route/location
* Read/unread state
* Action where applicable

---

# 2. PRIORITY

Use clear severity levels.

Example:

Informational
Warning
Critical

Do not make every alert look critical.

---

# 3. CONTEXTUAL ALERTS

Where appropriate, connect alerts to the active trip.

Example:

"Flooding reported 8 km ahead on your current route."

The interface should guide the driver toward the relevant action.

---

# 4. INCIDENT REPORTING

Allow Driver to report:

* Blocked road
* Road damage
* Flooding
* Landslide
* Accident
* Bridge issue
* Traffic obstruction
* Other disruption

Report fields:

* Type
* Severity
* Description
* Current GPS location
* Timestamp
* Photo/video where supported

---

# 5. REPORT UX

The reporting flow should be fast.

Use:

* Clear categories
* Minimal typing
* Large controls
* Optional voice/photo possibilities only if supported later

Do not make the reporting form unnecessarily long.

---

# 6. LOCATION

Automatically attach current location when permission/data is available.

Clearly show the captured location.

Allow safe correction if necessary.

---

# 7. OFFLINE PREPARATION

If the network is unavailable:

* Store the report locally.
* Mark it as pending.
* Show sync status.

Full offline synchronization architecture will be completed in Phase 2F.

---

# 8. DRIVER SAFETY / SOS

Provide a simple SOS flow.

Possible flow:

SOS
→ Confirmation
→ Capture current location
→ Show emergency state

Do not claim real emergency-service dispatch unless actually integrated.

Avoid accidental triggers.

---

# 9. ACCESSIBILITY & SAFETY

Important interactions must:

* Be easy to understand.
* Have clear confirmation.
* Avoid unnecessary steps.
* Work with touch.
* Use strong contrast.

---

# 10. SCOPE RESTRICTIONS

Do NOT build:

* Full notification infrastructure
* Emergency-service integrations
* Authority incident-management dashboard
* Full field-officer reporting system

The Driver-side functionality is the scope.

---

# 11. ACCEPTANCE CRITERIA

* Alerts are visible.
* Alert severity is clear.
* Driver can inspect alert details.
* Driver can report an incident.
* Location is attached where available.
* Report states are clear.
* SOS flow exists safely.
* Mobile experience is strong.
* No console errors.

# END PHASE 2E
